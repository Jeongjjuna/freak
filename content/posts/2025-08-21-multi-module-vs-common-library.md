## 서론

최근 기술 블로그나 컨퍼런스를 보면 `xxx-spring-boot-starter`와 같은 **공통 라이브러리**를 만들어 여러 서비스에서 사용하는 사례를 쉽게 찾아볼 수 있습니다. 저희 회사에서도 Spring Boot 기반의 공통 라이브러리를 만들어 여러 프로젝트에서 사용하고 있습니다.

프로젝트의 규모가 커지거나 여러 애플리케이션을 함께 개발하다 보면 **공통 코드를 어디에서 관리할 것인지** 고민하게 됩니다.
이번에는 Spring과 Gradle을 사용하면서 **공통 라이브러리와 멀티모듈을 어떤 상황에서 활용하는지**, 그리고 제가 멀티모듈을 구성할 때 중요하게 생각하는 기준을 정리해보려고 합니다.

아키텍처에는 절대적인 정답이 없으며, 프로젝트의 규모나 조직 구조, 배포 방식에 따라 적절한 선택은 달라질 수 있습니다. 저는 그중에서도 **변경과 배포를 어떻게 가져갈 것인지**를 중요한 기준으로 보고 있습니다.

<br><br>

## 1. 저는 이런 상황에서 공통 라이브러리를 사용합니다.

### [ 독립적인 프로젝트에서 공통 기능을 공유하는 경우 ]

제가 공통 라이브러리를 사용하는 대표적인 경우는 **서로 독립적으로 운영되는 프로젝트에서 공통 기능을 제공해야 하는 경우**입니다.
예를 들어 서로 다른 팀에서 독립적으로 운영하는 다음과 같은 서비스가 있다고 가정해보겠습니다.

```text
auth-server         # A팀
payment-server      # B팀
notification-server # C팀
```

각 프로젝트가 별도의 repository 에서 관리되고, 빌드와 배포 역시 독립적으로 이루어진다면 이를 하나의 멀티모듈 프로젝트로 묶어 관리하기보다는
**공통 기능을 라이브러리로 제공**하는 방식이 더 자연스러울 수 있습니다.<br>
이때 **팀과 프로젝트를 넘어 공통적으로 필요한 기능**이 있을 수 있습니다.

```text
common-library
├── 공통 API 응답 규격
├── 공통 Logging / Trace ID 처리
├── 공통 HTTP Client
└── Spring Boot 공통 설정
```

이런 경우에는 공통 기능을 라이브러리로 제공하고, 각 프로젝트에서 필요한 버전을 의존하도록 구성할 수 있습니다.

```text
auth-server
    └── common-library: 1.3.0
    
payment-server
    └── common-library: 1.2.0
    
notification-server
    └── common-library: 1.4.0
```

이 방식의 장점은 **공통 기능을 공유하면서도 각 프로젝트의 변경과 배포를 독립적으로 가져갈 수 있다는 점**입니다.<br>
예를 들어 `common-library: 1.4.0`이 배포되더라도 모든 프로젝트가 즉시 해당 버전을 적용할 필요는 없습니다.<br>
각 프로젝트의 상황과 일정에 맞춰 버전을 변경하고 배포할 수 있습니다.<br>
다만 저는 **코드가 여러 프로젝트에서 사용된다는 이유만으로 공통 라이브러리로 분리하는 것은 지양하는 편**입니다.<br>
공통 라이브러리로 분리하면 다음과 같은 관리 비용이 발생하기 때문입니다.

```text
공통 기능 변경
→ 라이브러리 수정
→ 라이브러리 버전 업
→ 각 프로젝트 의존성 변경
→ 각 프로젝트 테스트
→ 각 프로젝트 배포
```

프로젝트가 많아질수록 이러한 과정은 반복되고, 버전 간 호환성이나 라이브러리 자체의 안정성까지 함께 관리해야 합니다.

또한 라이브러리를 사용하는 각 서비스가 의도한 방식으로 사용할 수 있도록 가드레일을 정의하고, 필요한 경우 각 서비스의 상황에 맞게 확장할 수 있는 구조로 제공하는 세심함도 필요합니다.
(이 부분은 추후 사내 공통 라이브러리를 개발하면서 어떤 점을 고민하고 설계했는지 별도의 글에서 인사이트와 함께 공유해보겠습니다. 👍🏻)

특히 **조직 차원에서 동일한 규칙이나 구현 방식을 제공해야 하는 기능**이라면 공통 라이브러리로 관리하는 것이 유용합니다. 저는 사내 또는 전사적으로 **공통된 기능이나 기술적 규칙을 제공해야 하는 경우에만 최소한으로 추출해서 사용하는 편**입니다.

예를 들어 결제, 쿠폰, 인증과 같은 특정 도메인의 비즈니스 로직말고, 여러 프로젝트에서 **동일한 방식으로 적용해야 하는 기술적 공통 기능**이 공통 라이브러리에 더 적합할 수 있습니다.

- 공통 API 응답 규격
- Logging / Trace ID
- HTTP Client
- 인증 관련 공통 설정
- 공통 모니터링 및 인프라 연동

## 2. 그렇다면 언제 멀티모듈을 사용할까요?

### [하나의 플랫폼에서 여러 애플리케이션을 관리하는 경우]

저는 멀티모듈을 **하나의 플랫폼에서 여러 애플리케이션을 함께 관리하고, 변경도 함께 가져가는 것이 자연스러운 경우**에 고려합니다.<br>
예를 들어 쿠폰 플랫폼을 개발하고 있고 다음과 같은 애플리케이션이 필요하다고 가정해보겠습니다.

```text
coupon-platform
├── coupon-api
├── coupon-admin
├── coupon-batch
├── coupon-consumer
└── coupon-core # 쿠폰 플랫폼 내부의 도메인 공통 로직
```

각 애플리케이션은 서로 다른 역할을 담당합니다.

- `api` — 사용자 요청 처리
- `admin` — 관리자 기능 제공
- `batch` — 주기적인 작업 처리
- `consumer` — 메시지 기반 비동기 작업 처리

이처럼 **비즈니스적으로 관련된 애플리케이션이라면 하나의 repository 에서 모듈로 함께 관리하고, 각 애플리케이션은 독립적으로 빌드하고 배포하는 방식을 고려합니다.**

```
코드 관리 단위
    ↓
하나의 repository / 멀티모듈

배포 단위
    ↓
api.jar / admin.jar / batch.jar / consumer.jar
```

따라서 **코드의 관리 단위와 배포 단위는 반드시 동일할 필요가 없습니다.**

## 3. 멀티모듈을 구성할 때 제가 중요하게 보는 기준

멀티모듈을 구성할 때는 **모듈의 책임과 변경 단위**를 기준으로 나누려고 합니다.<br>
어떤 코드를 단순히 여러 곳에서 사용한다는 이유만으로 모듈로 분리하기보다는,

> "이 코드가 변경되었을 때 어디까지 함께 변경하고 배포하는 것이 자연스러운가?"
>

를 먼저 생각합니다.

이러한 관점은 인프콘에서 발표하신 **조민규님의 관련 글**을 읽으면서 좋은 인사이트를 얻을 수 있었습니다. 🙂

[[Server] 멀티 모듈을 설계하는 관점과 고려사항 with Spring & Gradle](https://mangkyu.tistory.com/304#google_vignette)

<br>

### [멀티모듈의 트레이드오프와 과도한 분리 피하기]

멀티모듈이라고 해서 가능한 한 많은 코드를 모듈로 분리하려고 하지는 않습니다.<br>
모듈을 분리할수록 다음과 같은 비용이 발생하기 때문입니다.

- 모듈 간 의존관계 관리
- Gradle 설정 증가
- 빌드 구조의 복잡도 증가
- 프로젝트 전체 구조를 이해해야 하는 비용

그래서 저는 **필요한 만큼만 최소한으로 모듈을 분리**하고, 실제로 책임이나 변경 단위의 경계가 명확한 경우에만 분리하는 편입니다.

![img_1.png](/images/posts/multi-module-vs-common-library/img_1.png)

특히 각 모듈의 의존관계를 Gradle을 통해 명시적으로 관리하고, **의도하지 않은 모듈 간 참조를 제한할 수 있다는 점**을 중요한 장점으로 보고 있습니다.

결국 멀티모듈의 목적을 **"코드를 최대한 잘게 나누는 것"이 아니라, 필요한 경계를 만들고 그 경계를 코드 수준에서 지키는 것**에 두고 있습니다.

특히 작은 프로젝트에서 단순히 패키지를 모듈로 승격시키는 방식으로 과도하게 분리하면 오히려 구조가 복잡해질 수 있습니다.

## 4. 마치며

멀티모듈과 공통 라이브러리 중 어느 하나가 항상 더 좋은 선택이라고 생각하지는 않습니다. (사실 둘은 엄격히 말하면 비교대상이라고 하기에는 애매한 부분이 있죠)

**공통 라이브러리**는 서로 독립적으로 운영되는 프로젝트에 공통 기능이나 기술적 규칙을 제공하면서, 각 프로젝트의 변경과 배포를 독립적으로 가져갈 수 있다는 장점이 있습니다.

반면 하나의 플랫폼 안에서 여러 애플리케이션을 함께 관리하고, 관련 코드의 변경사항을 함께 관리하는 것이 자연스럽다면 **멀티모듈**을 사용하는 편이 더 적합할 수 있습니다.

다만 두 방식 모두 과도하게 사용하면 새로운 복잡성이 생길 수 있습니다. 멀티모듈에서는 여러 모듈에서 사용하는 `core`나 `common`이 계속 커지면서 **거대한 공통 모듈**이 될 수 있고, 공통 라이브러리에서는 **버전 및 호환성 관리**가 추가적인 부담이 될 수 있습니다.

또한 **공통 라이브러리나 공통 모듈의 변경은 이를 사용하는 여러 서비스에 영향을 줄 수 있기 때문에, 변경 범위와 영향도를 고려해 신중하게 관리할 필요**가 있습니다.

따라서 단순히 "여러 곳에서 사용하는 코드인가?"만을 기준으로 결정하기보다는, 변경 주기와 서비스 간 결합도, 재사용 범위, 배포 방식, 서비스 영향도 등을 함께 고려할 필요가 있다고 생각합니다.

그중에서도 저는 **변경의 경계**를 판단하는 것을 중요하게 생각합니다.

> **"이 코드가 변경되었을 때 다른 코드도 함께 변경하고 검증해야 하는가?"**
>

변경을 함께 가져가는 것이 자연스럽다면 멀티모듈을, **프로젝트의 경계를 넘어 공통 기능을 제공하되 각 프로젝트의 변경과 배포는 독립적으로 가져가야 한다면** 공통 라이브러리를 고려합니다.

저도 처음에는 "왜 이렇게까지 복잡하게 모듈을 구성할까?"라는 생각도 했습니다.<br>

하지만 프로젝트 구조와 아키텍처, 유지보수와 배포에 대해 계속 고민하고 여러 개발자분들의 글과 사례를 찾아보면서, **왜 이런 구조를 선택했고 어떤 고민을 거쳐 지금의 형태가 되었는지** 조금씩 이해할 수 있었습니다.
실무에서 직접 고민하고 경험하다 보니 이런 관점들이 점점 머릿속에 자리 잡았고, 이제는 모듈이나 아키텍처를 볼 때도 **"왜 이렇게 구성했을까?"를 먼저 생각하게 된 것 같습니다.**

결국 정답이 있는 문제는 아니라고 생각합니다. 각자의 상황에서 필요한 기준을 세우고, 그 기준에 맞는 구조를 선택해보시면 좋을 것 같습니다.
감사합니다.
