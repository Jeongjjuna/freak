## 서론

최근에 여러 기술 블로그나 컨퍼런스를 보면 `xxx-spring-boot-starter`와 같은
**공통 라이브러리**를 직접 만들어 사용하는 사례를 쉽게 찾아볼 수 있었습니다.
마침 저희 회사에서도 비슷하게 여러 서비스에서 사용할 수 있는 공통 기능에대해 라이브러리를 만들어서
여러 프로젝트에 사용하고 있고, 이 과정에서 개발 생산성을 높이는 방법부터
유지보수성과 재사용성을 고려한 설계까지 다양한 고민을 이어가고 있습니다.<br>

<br>

MSA 환경에서 새로운 프로젝트를 구축하거나 여러 서비스에서 공통으로 필요한 기능이 생길 때마다,
각 프로젝트에 동일한 기능을 구현하고 배포하는 과정이 번거롭다고 느꼈습니다.
이러한 반복을 줄이고 공통 기능을 여러 프로젝트에서 일관되게 사용할 수 있도록 라이브러리를 만들기 시작했습니다.

<br>

SpringBoot(Gradle) 환경에서 공통기능 제공하기 위해서는
대표적으로 공통 라이브러리와 공통 모듈을 고려할 수 있습니다.  
이번 글에서는 두 방식의 차이와 각각 적합한 상황을 살펴보고,
멀티모듈을 구성할 때 제가 중요하게 생각하는 기준도 함께 정리해보겠습니다.

<br>

## 1. 공통 라이브러리를 선택하는 경우

### [ 프로젝트가 달라도 공통 기능을 재사용하고 싶을 때 ]

공통 라이브러리를 서로 다른 독립적인 프로젝트인데, 공통적인 기능을 제공하고 싶을 때 주로 사용합니다.

예를 들어, 서로 다른 팀에서 각각 운영하는 다음과 같은 서비스가 있다고 가정해 보겠습니다.

```text
auth-server         # A팀
payment-server      # B팀
notification-server # C팀
```

각 프로젝트는 담당하는 팀도 다르고 Git repository도 분리되어 있습니다.
빌드와 배포 역시 각 프로젝트에서 독립적으로 이루어집니다.

이처럼 서로 독립적인 프로젝트라도 사내에서 공통으로 사용하는 규칙이나 기능이 필요한 경우가 있습니다.
프로젝트마다 같은 기능을 반복해서 구현하기보다는,
공통 라이브러리로 만들어 필요한 프로젝트에서 가져다 쓸 수 있습니다.

예를 들면 다음과 같은 기능들입니다.

```text
common-library
├── 공통 API 응답 규격
├── 공통 Logging / Trace ID 처리
├── 공통 HTTP Client
└── 공통 도메인 용어 및 상수 정의
```

이런 경우에는 공통 기능을 라이브러리로 제공하고, 각 프로젝트에서 필요한 버전을 의존하도록 구성할 수 있습니다.
기능의 성격에 따라 Spring Boot AutoConfiguration으로 자동 설정을 제공하거나,
필요한 곳에서 직접 사용할 수 있는 유틸리티 형태로 제공하고 있습니다.

```kotlin
// auth-server
dependencies {
    implementation("xxx.common:xxx-spring-boot-starter:1.2.0")
}

// payment-server
dependencies {
    implementation("xxx.common:xxx-spring-boot-starter:1.4.0")
}
```

`xxx-spring-boot-starter: 1.4.0`이 배포되더라도 각 프로젝트의 상황과
일정에 맞춰 버전을 변경하고 배포하면 됩니다.
<br>

다만 저는 **코드가 여러 프로젝트에서 사용된다는 이유만으로 무조건 공통 라이브러리로 분리하는 것은 지양하는 편**입니다.<br>
공통 라이브러리로 분리하면 다음과 같은 관리 비용이 발생하기 때문입니다.

```text
공통 기능 변경
→ 라이브러리 수정
→ 라이브러리 버전 업
→ 각 프로젝트 의존성 변경
→ 각 프로젝트 테스트
→ 각 프로젝트 배포
```

그 외에도 **버전 간 호환성**, **라이브러리의 보안성**,
라이브러리를 사용하는 서비스들의 오사용에 대비한 **가드레일 전략**,
**개발 생산성**, **기술 확장성** 등 고민해야할 부분들이 정말 많습니다.

라이브러리를 개발하고 운영하며 고민해본 여러 케이스와 사례들이 있는데,
(이 부분은 추후에 어떤 점을 고민하고 설계했는지 별도의 글에서 인사이트와 함께 공유해보겠습니다. 👍🏻)

## 2. 멀티모듈로 구성하는 경우

### [ 하나의 플랫폼에서 여러 애플리케이션을 함께 관리할 때 ]

그렇다면 멀티모듈은 언제 사용할까요?  
저는 **하나의 플랫폼에서 여러 애플리케이션을 개발하고,
관련된 기능을 함께 수정하거나 관리해야 할 때** 멀티모듈을 고려합니다.

<br>

예를 들어 쿠폰 플랫폼을 개발하고 있고, 다음과 같은 애플리케이션이 필요하다고 가정해 보겠습니다.

```text
coupon-platform
├── coupon-api
├── coupon-admin
├── coupon-batch
├── coupon-consumer
└── coupon-core # 쿠폰 플랫폼 내부의 도메인 공통 로직
```

각 애플리케이션은 서로 다른 역할을 담당합니다.

- `api` — 사용자 요청 처리
- `admin` — 관리자 기능 제공
- `batch` — 주기적인 작업 처리
- `consumer` — 메시지 기반 비동기 작업 처리
- `core` — 쿠폰 상태, 쿠폰 도메인(쿠폰정보, 쿠폰사용)등 여러 모듈 공통으로 사용하는 핵심 비즈니스

이처럼 하나의 Git Repository에서 여러 애플리케이션을 함께 관리하면서,
공통으로 사용하는 비즈니스 로직은 별도 모듈로 분리해 재사용할 수 있습니다.
각 애플리케이션은 필요한 모듈을 가져다 사용하고, 빌드와 배포는 각각 독립적으로 진행할 수 있습니다.

```
코드 관리 단위
    ↓
하나의 repository / 멀티모듈

배포 단위
    ↓
api.jar / admin.jar / batch.jar / consumer.jar
```

## 3. 멀티모듈을 구성하면서 고민했던 것들

멀티모듈을 어떻게 구성할 것인가에 대해서는 많은 자료들과 여러 개발자분들의 경험을 토대로 봤을때 정답이 없습니다.

팀이 관리하는 소스코드, 빌드, 운영 규칙등에 따라서 적절히 나눠서 관리해야하고
너무 과하게 모듈을 나누면 오히려 복잡성만 높아질 수 있습니다.

그래서 저는 모듈을 나눌때 최소한으로 나누려고 의식하고 있고,
**모듈의 책임과 변경 단위**가 같은것끼리 나누려고 하고 있습니다.<br>
"단순히 같은 코드를 사용하니 하나의 모듈로에 모아놓고 가져다가 사용하자"
라는 이유만으로 모듈로 분리하기보다는,

> "이 코드가 변경되었을 때 어디까지 함께 변경하고 배포하는 것이 자연스러운가?"
>

를 먼저 생각합니다.(공통으로 사용하는 하위모듈을 수정하면, 상위모듈도 전부 함꼐 영향을 받고 배포범위에 들어가기 때문입니다.)


이러한 관점은 인프콘에서 발표하신 **조민규님의 관련 글**을 읽으면서 좋은 인사이트를 얻을 수 있었습니다. 🙂

### [ 모듈은 어디까지 나누는 게 좋을까? ]

앞서 설명한 것처럼, 멀티모듈을 구성한다고 해서 가능한 한 많은 코드를 모듈로 분리할 필요는 없습니다.
모듈이 늘어날수록 다음과 같은 비용도 함께 발생하기 때문입니다.

- 모듈 간 의존관계 관리
- Gradle 설정 증가
- 빌드 구조의 복잡도 증가
- 프로젝트 전체 구조를 이해해야 하는 비용

**필요한 만큼만 모듈을 분리**하고,
책임이나 변경 단위의 경계가 명확한 경우에만 분리하는게 좋습니다.

![img_1.png](/images/posts/multi-module-vs-common-library/img_1.png)

특히 각 모듈의 의존관계를 Gradle을 통해 명시적으로 관리하고,
**의도하지 않은 모듈 간 참조를 제한할 수 있다는 점**을 큰 장점으로 보고 있습니다.

제가 생각하는 멀티모듈의 장점은 단순히 공통 코드를 분리할 수 있다는 것이 아니라,
**모듈 간 의존관계를 명시하고 컴파일 시점에 강제할 수 있다는 점**입니다.

따라서 단순히 코드를 분리하는 데 집중하기보다는, 모듈을 나눴을 때
의존관계가 더 명확해지고 불필요한 참조를 줄일 수 있는지를 기준으로 판단하는 것이 좋다고 생각합니다.

## 4. 마치며

멀티모듈과 공통 라이브러리를 잘 활용하면 반복적인 작업을 줄이고,
팀이 핵심 비즈니스 개발에 더 집중할 수 있다고 생각합니다.

두 방식 모두 장단점이 있지만, 개인적인 경험상 언어와 프레임워크에 대한 이해를 바탕으로
에이전틱 코딩을 잘 활용한다면 유지보수 부담을 줄이고 개발 생산성을 높이는 데 도움이 되는 것 같습니다.

실제로 공통 라이브러리를 유지보수하면서 버전 관리, 테스트, 영향도 확인, 하위 호환성 검증,
휴먼 에러 방지 등을 위해 에이전틱 코딩을 활용하고 있습니다.

다만 공통 라이브러리나 모듈의 변경은 이를 사용하는 여러 서비스에 영향을 줄 수 있는 만큼,
단순히 "여러 곳에서 공통으로 사용하는 기능이니까 라이브러리로 만들자!" 보다는,
**변경 주기와 영향 범위, 배포 방식 등을 함께 고려해서 코드 구조를 설께하는 것이 중요한것 같습니다.**

다음 글에서는 공통 라이브러리를 개발하면서 고민했던 설계 방향과 구현 과정,
제공하는 기능들, 그리고 실제로 얻을 수 있었던 효과에 대해 공유해보겠습니다.
