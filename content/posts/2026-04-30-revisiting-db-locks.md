Lock을 이용해 여러 요청의 처리를 제어할 수도 있습니다.

2. DB 제약 조건 활용 (Unique Key 등)
3. DB Lock (비관적 락, 낙관적 락)
4. 비동기 순차 처리 (Queue 기반)

예전에 충분히 공부했다고 생각했던 내용도 다시 살펴보면 놓쳤던 부분이 보이곤 합니다.

각각 어떤 상황에서 활용하면 좋을지 정리해 보겠습니다.

## 동시성 문제

여러 요청이 동시에 같은 데이터에 접근하면, 요청이 각각 정상적으로 처리되더라도 예상하지 못한 결과가 발생할 수 있습니다.

대표적인 문제는 다음과 같습니다.

- Lost Update: 한 요청의 변경 사항이 다른 요청의 변경으로 덮어써지는 문제
- Race Condition: 실행 순서나 타이밍에 따라 결과가 달라지는 문제
- 데이터 불일치: 여러 요청이 데이터를 변경하는 과정에서 정합성이 깨지는 문제

이러한 문제는 좋아요 수 증가, 주문 생성, 재고 감소, 포인트 증가·차감처럼 여러 요청이 같은
데이터를 변경할 수 있는 기능에서 특히 주의해야 합니다.

따라서 기능을 개발할 때는 동시 요청이 발생할 가능성이 있는지, 어떤 데이터의 정합성을 보장해야 하는지 함께 고려해야 합니다.
데이터베이스는 이러한 동시 접근을 제어하기 위한 방법 중 하나로 Lock 메커니즘을 제공합니다.

## Record Lock (Row Lock)

Record Lock은 특정 레코드에 설정되는 잠금입니다.
InnoDB에서는 UPDATE, DELETE 등의 작업을 수행할 때 대상 레코드에 배타적 잠금(X Lock)을 획득할 수 있습니다.
다른 트랜잭션이 같은 레코드를 수정하려고 하면 기존 트랜잭션이 종료될 때까지 대기합니다.
즉, 같은 레코드에 대한 동시 쓰기를 제어하는 방식입니다.

### 락 상태 확인하기

실제로 어떤 Lock이 설정되는지 확인해 보겠습니다.
MySQL에서는 performance_schema.data_locks를 통해 현재 설정된 Lock을 조회할 수 있습니다.

```mysql
select *
from performance_schema.data_locks;
```

먼저 트랜잭션을 시작하고 특정 게시글의 좋아요 수를 증가시킵니다.
```mysql
START TRANSACTION;

UPDATE article
SET like_count = like_count + 1
WHERE id = 123;
```

해당 시점에 InnoDB는 id = 123 레코드에 대해 Exclusive Row Lock(X Lock) 을 획득합니다.
performance_schema 를 통해 조회해보면 아래와 같이 record lock 이 걸렸음을 확인할 수 있습니다.

```mysql
+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+---------------+-------------+-----------+
| ENGINE | ENGINE_LOCK_ID                            | ENGINE_TRANSACTION_ID | THREAD_ID | EVENT_ID | OBJECT_SCHEMA | OBJECT_NAME | PARTITION_NAME | SUBPARTITION_NAME | INDEX_NAME | OBJECT_INSTANCE_BEGIN | LOCK_TYPE | LOCK_MODE     | LOCK_STATUS | LOCK_DATA |
+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+---------------+-------------+-----------+
| INNODB | 281473586793688:112:1068:281473500370112  |                  1844 |        46 |       68 | lock_test     | article     | NULL           | NULL              | NULL       |       281473500370112 | TABLE     | IX            | GRANTED     | NULL      |
| INNODB | 281473586793688:112:2:4:2:281473500367120 |                  1844 |        46 |       68 | lock_test     | article     | NULL           | NULL              | PRIMARY    |       281473500367120 | RECORD    | X,REC_NOT_GAP | GRANTED     | 1         |
+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+---------------+-------------+-----------+
```

그래서 또다른 커넥션에서 아래와 같이 같은 record 에 대해 update 를 시도합니다.
```mysql
START TRANSACTION;

UPDATE article
SET like_count = like_count + 1
WHERE id = 123;
```

첫 번째 트랜잭션이 아직 종료되지 않았기 때문에 두 번째 UPDATE는 대기하게 됩니다.
첫 번째 트랜잭션에서 COMMIT 또는 ROLLBACK을 실행하면 Lock이 해제되고, 대기하던 UPDATE가 이어서 실행됩니다.
이렇게 같은 레코드를 수정하는 요청은 한 번에 하나씩 처리됩니다.

### WHERE 조건에 따라 달라지는 Lock

```mysql
UPDATE article SET like_count = like_count + 1 WHERE title = 'lock test article';

+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+-----------+-------------+------------------------+
| ENGINE | ENGINE_LOCK_ID                            | ENGINE_TRANSACTION_ID | THREAD_ID | EVENT_ID | OBJECT_SCHEMA | OBJECT_NAME | PARTITION_NAME | SUBPARTITION_NAME | INDEX_NAME | OBJECT_INSTANCE_BEGIN | LOCK_TYPE | LOCK_MODE | LOCK_STATUS | LOCK_DATA              |
+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+-----------+-------------+------------------------+
| INNODB | 281473586793688:114:1068:281473500370112  |                  1846 |        46 |       72 | lock_test     | article     | NULL           | NULL              | NULL       |       281473500370112 | TABLE     | IX        | GRANTED     | NULL                   |
| INNODB | 281473586793688:114:2:4:1:281473500367120 |                  1846 |        46 |       72 | lock_test     | article     | NULL           | NULL              | PRIMARY    |       281473500367120 | RECORD    | X         | GRANTED     | supremum pseudo-record |
| INNODB | 281473586793688:114:2:4:2:281473500367120 |                  1846 |        46 |       72 | lock_test     | article     | NULL           | NULL              | PRIMARY    |       281473500367120 | RECORD    | X         | GRANTED     | 1                      |
+--------+-------------------------------------------+-----------------------+-----------+----------+---------------+-------------+----------------+-------------------+------------+-----------------------+-----------+-----------+-------------+------------------------+
```

PK 조건을 사용했을 때와 달리, 조회 조건에 따라 여러 레코드가 대상이 될 수 있습니다.
또한 InnoDB에서는 실행 계획과 인덱스, 트랜잭션 격리 수준 등에 따라 Gap Lock이나 Next-Key Lock이 설정될 수도 있습니다.
이 경우 조회된 레코드뿐 아니라 특정 범위에 대한 INSERT가 대기할 수도 있습니다.
따라서 Lock의 범위를 이해하려면 WHERE 조건만 보는 것이 아니라 실제 인덱스와 실행 계획, 트랜잭션 격리 수준도 함께 확인해야 합니다.

## 락을 오래 점유하면 생기는 문제

Lock을 오래 점유하면 같은 레코드에 접근하려는 트랜잭션이 대기하게 됩니다.
대기하는 요청이 늘어나면 커넥션 풀이 고갈될 수 있고, 응답 지연이 다른 요청으로까지 이어질 수 있습니다.
여러 트랜잭션이 서로의 Lock을 기다리면 Deadlock이 발생하기도 합니다.
따라서 Lock을 사용하는 것뿐 아니라, 얼마나 짧게 점유하고 해제할 수 있는지도 함께 고려해야 합니다.

## 조회수, 좋아요 기능 예시

자주 나오는 예시로 게시글 서비스에서는 조회수나 좋아요 수를 게시글 테이블에 함께 저장하기도 합니다.
이때 조회수 증가, 좋아요 증가, 게시글 수정이 모두 같은 게시글 레코드를 변경한다면
서로 다른 기능간의 요청도 Lock 경합을 일으킬 수 있습니다.

특정 게시글에 요청이 집중될수록 집계 데이터의 업데이트가 다른 작업의 대기로 이어질 가능성도 커집니다.

## 데이터 구조 분리를 통한 Lock 경합 완화

이런 경우 데이터의 역할을 나누는 방법을 고려할 수 있습니다.

- article: 게시글 본문과 기본 정보
- article_like: 사용자별 좋아요 정보
- article_like_count: 좋아요 집계 정보

예를 들어 좋아요 정보를 별도 테이블에 저장하면 게시글 본문을 수정하는 작업과 좋아요를 처리하는 작업이
같은 레코드에 집중되는 상황을 줄일 수 있습니다.

조회수처럼 정확한 실시간 반영이 필요하지 않은 데이터라면
요청마다 DB를 갱신하는 대신 캐시에 누적한 뒤 일정 주기로 반영하는 방법도 있습니다.

다만 테이블을 분리한다고 모든 Lock 경합이 사라지는 것은 아닙니다.
분리한 집계 레코드에 요청이 집중되면 여전히 경합이 발생할 수 있습니다.

결국 동시성 문제는 Lock 설정만으로 해결하기보다 데이터 구조와 업데이트 방식을 함께 살펴봐야 합니다.

## 비관적 락 (Pessimistic Lock)

비관적 락은 데이터 충돌이 발생할 가능성이 높다고 보고, 먼저 잠금을 획득해 충돌을 제어하는 방식입니다.

InnoDB의 레코드 잠금은 이런 잠금 동작을 구현하는 데 사용됩니다.
애플리케이션에서는 대표적으로 SELECT ... FOR UPDATE를 이용해 비관적 락을 사용할 수 있습니다.

### 방법 1 — UPDATE 한 번에 처리

```mysql
UPDATE article
SET like_count = like_count + 1
WHERE id = 123;
```

단순한 증가·감소 연산이라면 별도로 조회하지 않고 UPDATE 한 번으로 처리할 수 있습니다.

- UPDATE 과정에서 필요한 잠금 획득
- 별도 조회 없이 원자적으로 값 변경
- 불필요한 애플리케이션 로직과 잠금 점유 시간 감소

단순한 카운터 변경이라면 먼저 이 방법으로 해결할 수 있는지 살펴보는 것이 좋습니다.

### 방법 2 — SELECT FOR UPDATE

```mysql
START TRANSACTION;

SELECT *
FROM article
WHERE id = 123
    FOR UPDATE;

-- 조회한 데이터를 검증하고 필요한 작업 수행

UPDATE article
SET like_count = like_count + 1
WHERE id = 123;

COMMIT;
```

조회한 데이터를 검증한 뒤 수정해야 한다면 SELECT ... FOR UPDATE를 사용할 수 있습니다.
조회 시점부터 대상 레코드에 잠금을 설정하므로, 다른 트랜잭션의 변경을 기다리게 할 수 있습니다.
다만 잠금을 획득한 상태에서 복잡한 비즈니스 로직을 수행하면 점유 시간이 길어질 수 있습니다.
트랜잭션 안에서 불필요한 외부 API 호출이나 오래 걸리는 작업을 하지 않도록 주의해야 합니다.

## 낙관적 락 (Optimistic Lock)

낙관적 락은 충돌이 자주 발생하지 않는다고 가정하고, 실제 데이터를 변경하는 시점에 충돌 여부를 확인하는 방식입니다.
일반적으로 데이터에 version 컬럼을 두고, 수정할 때 조회했던 버전이 여전히 유효한지 확인합니다.

### 동작 방식

- 현재 version 조회
- UPDATE 시 version 조건 포함
- 수정 성공 시 version 증가

```mysql
UPDATE article
SET like_count = 10,
    version = version + 1
WHERE id = 123
  AND version = 10;
```

다른 트랜잭션이 먼저 데이터를 수정해 버전이 변경됐다면 UPDATE 결과는 0건이 됩니다. 이를 통해 충돌을 감지할 수 있습니다.
다만 낙관적 락도 UPDATE 과정에서 DB Lock을 사용합니다.

비관적 락처럼 미리 잠금을 획득해 대기시키는 대신, 버전 검증을 통해 충돌을 감지한다는 점이 다릅니다.
충돌이 발생했을 때는 무조건 재시도하기보다 비즈니스 요구사항에 따라 재시도하거나 실패를 반환하는 등 적절한 처리 방식을 정해야 합니다.

낙관적 락은 충돌이 비교적 적고, 다른 트랜잭션의 잠금 해제를 기다리는 상황을 줄이고 싶을 때 고려할 수 있습니다.

## 마무리

동시성 문제를 해결할 때는 먼저 Lock부터 적용하기보다,
데이터 구조나 업데이트 방식을 바꿔 경합을 줄일 수 있는지 살펴보는 것이 좋습니다.

이번에 다시 정리하면서 동시성 문제를 검토할 때 다음 순서로 생각해 보면 좋겠다고 느꼈습니다.

- 데이터 구조를 분리할 수 있는가?
- 원자적인 UPDATE로 해결할 수 있는가?
- 비관적 락이나 낙관적 락이 필요한가?
- 비동기 처리를 통해 요청을 분산하거나 순차 처리할 수 있는가?
- 여러 인스턴스에서 공유 자원을 제어해야 한다면 분산 락이 적절한가?

각 방법은 보장하는 내용과 운영상 고려할 점이 다릅니다.
해결하려는 문제와 정합성 요구사항에 맞춰 선택하는 것이 중요합니다.

오랜만에 DB Lock을 다시 살펴보면서, 동시성 문제는 단순히 잠금 기술을 적용하는 것뿐 아니라
데이터 구조와 처리 흐름을 함께 고민해야 한다는 점을 다시 정리할 수 있었습니다.
